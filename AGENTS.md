# Agent guide

## Objective

Produce an algorithmic `frame,label` prediction for all 199,319 match frames. Each label must be:

- `H`: home possession while the ball is live
- `A`: away possession while the ball is live
- `D`: ball not in play
- `X`: abstain or no ground truth

Treat possession as persistent through loose balls, deflections, and contests. Change teams only
when the opponent gains controlled possession. A restart begins a new possession; a dead-ball run
is a stoppage, not a possession.

## Priorities

1. Optimise `spellF1`, the ranking metric; use `macroF1` as the tie-break and diagnostic.
2. Prefer stable, whole possession spells over noisy frame-by-frame switches.
3. Use `X` only deliberately. During scoring it behaves like a miss for `macroF1`; for `spellF1`
   it is filled with the preceding label in the same half, which is risky across turnovers.
4. Assume all provided tracking, tagging, and homography data is automatic and noisy. Ball tracking
   is missing on many graded frames; do not equate missing data with `D` or `X` automatically.
5. Use the public five-minute ground truth to understand and test the pipeline, not to hand-tune
   labels for the supplied match. The ground truth definition wins over heuristic interpretations.

## Constraints

- Labels must be generated by an algorithm. Never manually annotate the provided match or use hand
  labels from it for training or validation.
- Do not rebuild object tracking or game state unless a measured improvement requires it; the core
  problem is inferring live/dead state and controlled possession from the supplied data.
- Keep solutions reproducible and document data sources, assumptions, preprocessing, models, and
  post-processing for the technical submission.
- Preserve compatibility with Python 3.8+ unless a documented optional component requires newer
  Python. Prefer existing dependencies and repository loaders before adding packages.
- Read `RULES.md` before introducing external data, models, or services.

## Repository workflow

- Start from `starter/baseline.py` and the loaders in `starter/`.
- Use `games.py` for match constants, asset paths, and frame alignment.
- Read `DATA.md` before changing alignment or interpreting an asset.
- Read `EVALUATION.md` before changing smoothing, transition handling, or abstention behavior.
- Write experimental submissions under `evaluation/results/`; do not alter public ground truth.
- Keep changes small and evidence-driven. Compare against the included baseline and report both
  metrics, possession count, and mean possession duration.

## Required checks

```bash
python evaluation/run_evaluation.py
python evaluation/validate_submission.py <submission.csv>
```

Run the validator on every final CSV. A valid submission must contain exactly one row per match
frame with the expected frame numbers, column names, and allowed labels. Consult `SUBMISSION.md`
for the full delivery contract.
